
- Multi-rôles : AuthContext lit tous les rôles de user_roles ; mono-rôle = identique, multi-rôle = choix mémorisé (logisorama.active-role) sinon priorité. Why: double rôle candidat+client sans casser les comptes existants.
- Candidat→client uniquement via RPC activate_candidat_searches (SECURITY DEFINER). Why: jamais d’INSERT libre dans user_roles.
- Tableau candidat : réutiliser la couverture, l'entête, les pastilles et les tuiles client avec des destinations candidat ; agenda et messages candidat restent isolés des routes client protégées. Why: cohérence visuelle sans élargir les accès ni changer les espaces mono-rôle.
- Critères candidat : table candidat_criteres (1 ligne/user, RLS propriétaire + lecture admin/agent), formulaire = MandatFormStep4 réutilisé, écran bloquant CandidatCriteresGate sur routes candidat ; pré-remplit /nouveau-mandat via son brouillon localStorage. Why: cohérence client et aucun changement du formulaire mandat.
- Mobile app shell: anchor the shared shell to the dynamic viewport and let its internal main area scroll; nested mobile messaging fills that area instead of calculating its own viewport height. Why: keeps the bottom navigation at the screen edge in iOS standalone mode without double-counting safe areas.
- Candidate visit registration accepts an omitted slot only for new-account creation, never assigning a role to an existing email without authentication. Why: full slots must allow signup without creating a visit or escalating another user's account.
- Public homepage featured properties query published, unexpired, highlighted Immo-Rama listings directly; connected-area showcase stories remain separate. Why: the homepage must never mix sourced external offers or visits into its property carousel.
- Candidature documents: text comes verbatim from candidature_documents.contenu_html; signatures are overlaid at render time (src/lib/candidatureDocs.ts) and PDFs stored in the private candidature-documents bucket under <candidature_id>/. Why: never alter legal wording in the client.
- Sidebar sections derive from the real active role and resolved client journey; persist their expanded state per role and section, without changing route permissions. Why: navigation preferences must not impersonate roles or grant data access.
- PWA updates require an explicit user action before reloading; stale route chunks get at most one shared reload attempt per tab. Why: preserve in-progress work without trapping users in refresh loops.
- Sidebar route code prefetch uses the exact protected-route import map and only warms modules on intent or idle; vendor chunks group shared dependencies. Why: speed repeat navigation without mounting unauthorized pages or increasing initial data requests.
- Client postulation requests go only through RPC request_postulation, which queues postulation_jobs processed by process-postulation-job (immediate invoke + 1-min sweep); the pipeline never submits to a régie. Why: idempotent clicks and a single supervised staff queue.
- Steeve 3D (<steeve-mascot>, src/components/steeve) is the only messaging launcher: one SteeveLauncher per layout, driven by the real messenger state (open, unread, busy), on the project's single Three.js version; the mascot never stores messages and 'success' is only played after a confirmed business result. Why: one trigger, no duplicate Three.js, no simulated confirmations.
- Steeve opérateur (supabase/functions/steeve-operator, _shared/steeve/operator.ts) n'envoie qu'après contrôle et journalise chaque action dans steeve_actions avec une clé unique ; mode réglé par l'admin (off / a_blanc 48 h / autonome), envois 7h–20h ; visites, QR et relances depuis visites@, dossiers depuis relocation@ ; dossier retenu et bail : Steeve met la candidature à jour et prévient le client, l'équipe garde bail, signature, garantie et paiement ; questions des régies restent humaines. Why: autonomie sans double envoi ni action irréversible non tracée.
- Steeve cherche et envoie lui-même des offres (supabase/functions/_shared/steeve/offers.ts, tâche recherche_offres) avec le mode d'emploi des routines d'offres : clients servis, plafond revenus ÷ 3, 6 offres/jour toutes sources, exigences écrites prouvées, score 80 avec visite / 90 sans, aucun doublon, gabarit buildOffreMessage. Demandée par un humain : faite tout de suite ; automatique : suit le mode. Why: le client reçoit des offres dès qu'il change ses critères, sans offre hors critères.
- Conversation « Steeve » de l'admin (conversations.conversation_type = 'steeve-admin', une par admin, admin_user_id) : Steeve y poste les demandes à valider (propositions, transferts, alertes de l'opérateur, « contacter l'équipe » des partenaires) par triggers ; la réponse de l'admin appelle steeve-admin avec { conversation_id } (session de l'admin), qui agit avec ses outils puis répond à la personne (steeve_admin_ecrire : conversation du client, sinon notification). Why: une seule boîte de décision pour l'admin, et la personne reçoit la réponse sans ressaisie.
